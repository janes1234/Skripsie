\mychapter{Experimental Design}{Experimental Design}{}\label{chap:experimental_design}

\section{Overview}
\label{sec:exp_overview}

This chapter describes how the classification system was designed and configured, and which experiments were run with it. The clarifiers and the aerobic zones are treated as two separate classification problems (Chapter~\ref{chap:systemmethods}), but both are handled by the same system, and every experiment is carried out for both components unless stated otherwise. The first part covers the parts of the system that are shared by every experiment: the model architectures and how transfer learning is applied to them (Section~\ref{sec:exp_architectures}), the augmentations applied to the training images (Section~\ref{sec:exp_augmentation}), how the class imbalance in the dataset is handled (Section~\ref{sec:exp_loss}), how the hyperparameters of each architecture were chosen (Section~\ref{sec:exp_hyperparams}), and the training loop itself (Section~\ref{sec:exp_training}).

The second part describes the three experiments that were carried out using this system:

\begin{enumerate}
    \item \textbf{Mixed-facility baseline} (Section~\ref{sec:exp_mixed}): the images of all five facilities are pooled and divided using the stratified 70/20/10 training/development/test split described in Chapter~\ref{chap:systemmethods}.
    \item \textbf{Leave-one-facility-out evaluation} (Section~\ref{sec:exp_lofo}): each facility is held out in turn as an unseen test facility, while the model is trained on the remaining facilities, with part of them held out as a development set. This gives five folds for the clarifiers, and three for the aerobic zones, which are only labelled at three facilities. This experiment estimates how well a model would perform on a facility it has never seen before.
    \item \textbf{Binary (OK / Not-OK) approach} (Section~\ref{sec:exp_binary}): the classes are collapsed into a two-class problem, where \textbf{Functional} is treated as OK and every other class is treated as Not-OK: \textbf{Dysfunctional}, \textbf{Empty} and \textbf{Scum} for the clarifiers, and \textbf{Suboptimal} and \textbf{Dysfunctional} for the aerobic zones.
\end{enumerate}

The chapter ends with the metrics used to evaluate every run (Section~\ref{sec:exp_metrics}) and the Grad-CAM method used to inspect which parts of an image a model bases its prediction on (Section~\ref{sec:exp_gradcam}).

Figure~\ref{fig:experimental_pipeline} summarises the pipeline from start to finish. It starts from the labelled satellite images described in Chapter~\ref{chap:systemmethods}, which \texttt{prep.py} crops into individual images sorted into one folder per class. These images are then divided into training, development and test sets, either with the stratified split of Experiment~1 or by facility, so that no image from the held-out test facility is ever used during training. Every image is resized and normalised before it is passed to the network, and images in the training set are also randomly augmented (Section~\ref{sec:exp_augmentation}). The network is one of the seven architectures in Section~\ref{sec:exp_architectures}, with a classifier head sized by the hyperparameters chosen for that architecture (Section~\ref{sec:exp_hyperparams}), and is trained using the loop described in Section~\ref{sec:exp_training}.

The results of every run, meaning one architecture trained for one component on one split, are saved to a separate \texttt{results\_*.pkl} file (Section~\ref{sec:exp_lofo}). Each file contains the test metrics, the confusion matrix, the training history and the classification made for every test image.


\section{Model Architectures and Transfer Learning}\label{sec:exp_architectures}

Seven CNN architectures are compared in this project: ResNet-18 and ResNet-50 (Section~\ref{sec:resnet}), DenseNet-121 (Section~\ref{sec:densenet}), Inception-v3 (Section~\ref{sec:inception}), EfficientNet-B0 (Section~\ref{sec:efficientnet}), ConvNeXt-Tiny (Section~\ref{sec:convnext}) and AlexNet. Table~\ref{tab:arch_sizes} lists their sizes, which range from 5.3 to 61.1 million parameters. All seven are taken from the torchvision library, and the same seven architectures are trained for both the clarifiers and the aerobic zones.

AlexNet is deliberately different from the other six: rather than being fine-tuned from ImageNet weights, it is trained entirely from randomly initialised weights, with its own separate, hand-picked configuration (Section~\ref{sec:exp_hyperparams}). It was added to the project specifically to measure the effect of pretraining, that is, whether the far larger pretrained architectures outperform a classical network trained from scratch on this project's own, small dataset.

For each of the six pretrained architectures, transfer learning follows the same recipe. The architecture's convolutional backbone is loaded with weights pretrained on ImageNet~\citep{deng2009imagenet}, specifically torchvision's \texttt{IMAGENET1K\_V1} weights, except for ResNet-50, which uses the newer, more accurate \texttt{IMAGENET1K\_V2} recipe. Its original 1000-class ImageNet output layer is then discarded, and a new classifier head, sized by that architecture's own tuned hidden layers ($H$) and neurons ($N$) (Section~\ref{sec:exp_hyperparams}), is put in its place: a stack of $H$ \texttt{Linear+ReLU} pairs followed by a final \texttt{Linear} layer mapping to the project's number of classes. Every parameter in the network, backbone included, is then fine-tuned on the WWTW dataset. No layers are frozen, so pretraining only supplies a starting point for every weight rather than fixing any of them in place.

Every one of these architectures ends in the same kind of structure: a convolutional backbone feeding into one or more fully connected layers that produce the 1000 ImageNet class scores. Replacing this final part therefore means locating whichever attribute of the model object torchvision happens to store it under, which differs from one architecture's implementation to the next. For ResNet-18, ResNet-50 and Inception-v3, it is a single attribute named \texttt{model.fc}. DenseNet-121 stores the same kind of single layer under \texttt{model.classifier} instead, which is simply a difference in torchvision's naming convention rather than an architectural difference. For EfficientNet-B0, ConvNeXt-Tiny and AlexNet, \texttt{model.classifier} is itself a short stack of several layers rather than a single one, so only the specific layer within it that produces the final class scores, the last \texttt{Linear} layer, is replaced, and everything before it is left as it was. In practice, this means EfficientNet-B0 and AlexNet keep the dropout layer that is located just before the original output layer, and AlexNet also keeps its two existing hidden fully connected layers of 4096 neurons each, since these are simply the layers that fed into the one that got replaced.

Two architectures need one further, architecture-specific adjustment. Inception-v3's auxiliary classifier (Section~\ref{sec:inception}), used only during training, also has its own small output layer resized to the project's number of classes. Unlike the main classifier head, it is always left as a single \texttt{Linear} layer regardless of the tuned hidden layers ($H$) and nuerons ($N$), since it is only a secondary training signal rather than the model's final output. ConvNeXt-Tiny's global average pooling layer is replaced with global max pooling, so the feature vector reaching its classifier head is composed of each channel's strongest activation rather than its average.

Every image is resized to a fixed input size before it is passed to the network. The clarifier crops are close to square, since they are cut around a circular tank, and are resized to $224\times224$ pixels. The aerobic zones are wide rectangles, with a median width of about 2.6 times their height, and are resized to $112\times224$ pixels (height $\times$ width). This 2:1 shape is slightly less elongated than most of the crops, but keeps them much closer to their original shape than a square input would. Inception-v3 is the exception: it expects larger inputs, and every image is resized to $299\times299$ pixels for it, so the aerobic zones are stretched vertically to a square for this architecture. After resizing, every image is normalised with the mean and standard deviation of the ImageNet images, per colour channel, since the pretrained backbones were trained on inputs normalised in this way.


\section{Augmentation}
\label{sec:exp_augmentation}

Data augmentation makes small, random changes to the training images, so that the network sees a slightly different version of every image each time it is used. This increases the variety in the training data without collecting any new images, and makes it harder for the network to memorise individual images. Augmentation is applied to the training set only. The development and test images are never augmented, so that they are evaluated exactly as they are.

The augmentations are applied by PyTorch each time an image is loaded, rather than being generated once and saved to disk. The size of the training set therefore stays the same, but every epoch sees a new, randomly augmented version of each training image. Three augmentations are applied, in the following order:

\begin{itemize}
    \item \textbf{Horizontal flip}: the image is mirrored from left to right with a probability of 50\%.
    \item \textbf{Rotation}: the image is rotated by a random angle, chosen uniformly between $-15^\circ$ and $+15^\circ$. The output image keeps its original size, so the corners that are rotated out of the frame are cut off, and the empty corners that are rotated into the frame are filled with black.
    \item \textbf{Colour jitter}: the brightness, contrast, saturation and hue of the image are changed by a random amount, with the four adjustments applied in a random order. The brightness and contrast are each multiplied by a random factor between $0.6$ and $1.4$, the saturation by a random factor between $0.7$ and $1.3$, and the hue is shifted by up to $\pm 0.1$ of the full colour wheel (at most $36^\circ$).
\end{itemize}

The flip and rotation are suited to this dataset because the images are taken from directly above. A clarifier seen from above has no fixed orientation, so a mirrored or slightly rotated clarifier is still a realistic example of the same class. When \texttt{prep.py} crops a clarifier, it also sets every pixel outside the annotated circle to black, which matches the black corners introduced by the rotation. The aerobic zones do not have this black background, since their annotations are rectangles. For them, a rotation cuts off the ends of the zone and adds small black triangles along its edges. The rotation is limited to $\pm 15^\circ$, so most of the surface of the zone remains visible.

The colour jitter targets a different problem. The images come from different facilities and were captured on different dates, so the lighting, sun glare and water colour vary between images. The colour jitter is intended to stop the network from memorising the exact colour or brightness of the water at a particular facility, and to make it rely on other features of the clarifier instead.

The hue shift does raise a concern, since the clarifier classes are partly defined by colour, and a \textbf{Dysfunctional} clarifier is identified by its green surface (Chapter~\ref{chap:systemmethods}). A hue shift could wash out this green colour while the image keeps its \textbf{Dysfunctional} label. To test whether this harmed the models, all seven clarifier architectures were retrained on all five leave-one-facility-out splits with the hue shift disabled, keeping every other augmentation and hyperparameter the same. Disabling the hue shift did not affect performance, and so it was maintained (Section~\ref{sec:results_hue_ablation}). The aerobic zones use the same augmentations. Their classes are defined by the leopard print pattern on the surface rather than by its colour (Chapter~\ref{chap:systemmethods}), so the same concern applies less directly, and the hue shift was not tested separately for the aerobic zones.

\section{Class Imbalance}
\label{sec:exp_loss}

As shown in Tables~\ref{tab:aerobic_summary} and~\ref{tab:clarifier_summary} in Section~\ref{sec:final_dataset}, the classes of both components are highly imbalanced. For the clarifiers, \textbf{Functional} and \textbf{Scum} clarifiers make up most of the dataset (2090 of the 2527 images), while \textbf{Dysfunctional} and especially \textbf{Empty} clarifiers are much less common. For the aerobic zones, \textbf{Suboptimal} is the rare class, with only 223 of the 1743 images. If every image contributes equally to the loss, the network can reach a low loss by mostly predicting the common classes, and has little incentive to learn the rare ones.

To counter this, the cross-entropy loss is weighted per class, so that the network is penalised more for misclassifying an image from a rare class than from a common one. The weight of each class is inversely proportional to the number of training images in that class, and the weights are then normalised so that they sum to the number of classes. For $K$ classes, where $n_c$ is the number of training images in class $c$, the weight of class $c$ is

\begin{equation}
    w_c = K \cdot \frac{1/n_c}{\sum_{j=1}^{K} 1/n_j}.
\end{equation}

A class with average representation therefore gets a weight close to one, a rare class gets a weight larger than one, and a common class gets a weight smaller than one. These weights are passed to PyTorch's \texttt{CrossEntropyLoss}, which multiplies the loss of each image by the weight of its true class. The training data itself is not resampled, so every training image is still used exactly once per epoch.

The weights are calculated from the training set only, and are recalculated for every split, since the class counts change depending on which facility is held out. For the clarifiers, the Cape Flats split stands out. Cape Flats contains 120 of the 145 \textbf{Empty} clarifiers in the dataset (Table~\ref{tab:clarifier_summary} in Section~\ref{sec:final_dataset}), so when it is held out for testing, only 25 \textbf{Empty} images are left, 21 of which are in the training set. The weight of the \textbf{Empty} class rises to 3.09 as a result, about twenty times the weight of the \textbf{Scum} class (0.15). In the same way, Northern Works contains 131 of the 292 \textbf{Dysfunctional} clarifiers, so holding it out raises the \textbf{Dysfunctional} weight to 1.55, compared with about 1.1 in the Atlantis, Fisantekraal and Waterval splits.

For the aerobic zones, \textbf{Suboptimal} has the highest weight in every split, between 1.48 and 1.90. The held-out facility again changes the weights of the other two classes. Waterval contains 543 of the 707 \textbf{Functional} aerobic zones, so when it is held out, \textbf{Functional} becomes a minority class in the training set, with a weight of 1.19 compared with 0.34 to 0.61 in the other splits. The Waterval test set is therefore dominated by a class that is comparatively scarce in its own training set. Similarly, Cape Flats contains 562 of the 813 \textbf{Dysfunctional} aerobic zones, and holding it out raises the \textbf{Dysfunctional} weight to 0.82, compared with 0.34 to 0.51 in the other splits.

The same weighted loss is also used to calculate the development loss. Since the development loss decides when training stops early and which epoch's weights are kept (Section~\ref{sec:exp_training}), the class weighting also influences model selection, and not only the gradient updates during training.


\section{Hyperparameter Tuning}
\label{sec:exp_hyperparams}

Some hyperparameters were fixed for every architecture: Adam's $\beta_2$ ($0.999$, the default from Adam's original paper), the $L_2$ weight decay ($10^{-4}$), a maximum of 100 epochs, an early-stopping patience of 10 epochs and a random seed of 42. The remaining hyperparameters, namely the number of hidden layers $H$ and neurons per layer $N$ of the classifier head, the learning rate, Adam's $\beta_1$, the \texttt{StepLR} step size and the batch size, were tuned with Optuna~\cite{akiba2019optuna}, a hyperparameter optimisation library. This was done for six of the seven architectures, separately for the clarifiers and the aerobic zones, giving twelve searches. AlexNet was not tuned (Section~\ref{subsec:defaults}).

\subsection{Why Optuna}
\label{subsec:why_optuna}

The six tuned hyperparameters interact, so tuning them one at a time can miss good combinations, and a grid search over all six is too expensive. Optuna searches all six jointly with a Tree-structured Parzen Estimator (TPE) sampler, which samples new candidates from the regions of the search space where earlier trials scored well. A \texttt{MedianPruner} also stops a trial early if its development accuracy falls below the median of the earlier trials at the same epoch.

\subsection{Search Procedure}
\label{subsec:search_procedure}

The first ten trials of every search are sampled at random, and the last ten are guided by TPE. The pruner only becomes active after five trials have completed, and does not prune a trial before its fifth epoch. Every trial uses the same training loop as the final models (Section~\ref{sec:exp_training}) and is scored by its development accuracy at the epoch with the lowest development loss, which is the checkpoint that is kept when a model is trained.

To limit the compute cost, each search was run once, on the leave-one-facility-out fold with Northern Works held out, rather than on every fold. The selected values are used for every fold and for the stratified split (Sections~\ref{sec:exp_mixed} and~\ref{sec:exp_lofo}).

\subsection{AlexNet}
\label{subsec:defaults}

AlexNet is trained from randomly initialised weights rather than fine-tuned (Section~\ref{sec:exp_architectures}). It was not included in the search, and its values were chosen by hand and are the same for both components (Table~\ref{tab:hyperparams}). No hidden layers are added ($H{=}0$), since AlexNet's own classifier already contains two hidden layers of 4096 neurons. A first configuration with a learning rate of $10^{-3}$ and three added hidden layers of 1024 neurons often collapsed to predicting a single class, so the learning rate was lowered to $10^{-4}$ and the added layers were removed. $\beta_1$ is set to Adam's default of $0.9$. AlexNet is trained for the full 100 epochs without early stopping, since its development loss can stay on a plateau for many epochs before it starts to learn, and early stopping ended training too soon. The checkpoint with the lowest development loss is still the one that is kept.


\section{Training Procedure}
\label{sec:exp_training}

Every architecture is trained with the same procedure; only the specific hyperparameter values are different, as set out in Section~\ref{sec:exp_hyperparams}. 

Rather than using one fixed learning rate for an entire run, every architecture uses \texttt{StepLR} to cut the learning rate by a factor of ten every time a fixed, architecture-specific number of epochs (the step size) has passed (Section~\ref{sec:exp_hyperparams}), since large steps are useful early on to make fast progress but become counter-productive once the model is close to a good solution, where they cause it to overshoot instead of converging.

Training is allowed to run for up to 100 epochs, but is stopped early if development loss has not improved for 10 consecutive epochs, since the point at which a given architecture stops improving and starts overfitting is not known ahead of time and differs from one architecture to the next. AlexNet is the only exception, and always runs for the full 100 epochs (Section~\ref{subsec:defaults}). Development \emph{loss}, rather than accuracy, is used to decide both when to stop and which epoch's weights to keep: whichever epoch achieved the lowest development loss is the one whose weights are restored and carried forward to testing, rather than simply whatever weights training happened to end on. Figure~\ref{fig:training_flow} summarises this loop.

Inception-v3 is trained with one additional detail: during training only, it produces a second, auxiliary prediction partway through the network, and the loss from this auxiliary output is added to the main loss at a reduced weight of $0.4$. This gives the earlier layers of the network a more direct training signal than would otherwise reach them through such a deep network, and is discarded entirely once training finishes, playing no role in the model's actual predictions at test time.

The same fixed seed used throughout this project (Section~\ref{sec:exp_hyperparams}) also covers the random initialisation of each architecture's new classifier head and the order in which the training images are shuffled, in addition to the dataset splitting described in Chapter~\ref{chap:systemmethods}. A repeated run therefore starts from the same weights and splits. It is not guaranteed to reproduce the results exactly, however, since some GPU operations are not deterministic and mixed precision adds small rounding differences, so repeated runs can differ slightly.


\section{Experiment 1: Mixed-Facility Baseline}
\label{sec:exp_mixed}

The first experiment does not take into account which facility an image comes from. The images of all five facilities are pooled and divided into training, development and test sets using the stratified 70/20/10 split described in Chapter~\ref{chap:systemmethods}. The images are grouped by facility, unit and class, each group is shuffled using the fixed random seed of 42, and the group is then divided in a 70/20/10 ratio. A group with at least three images always receives at least one development image and one test image, even where rounding would otherwise leave it with none. Every facility, unit and class is therefore represented in all three sets, in proportion to the number of images it contributes. All seven architectures are trained using this division of the data, for both the clarifiers and the aerobic zones. Both components use the hyperparameter values optimised on the fold with Northern Works held out (Table~\ref{tab:hyperparams} in Section~\ref{sec:exp_hyperparams}).

Experiment~1 is also used to measure the effect of augmentation. Every architecture is trained a second time on the same data but without augmentation (resizing and normalisation is maintained for all train, development and test images). The data, hyperparameters, class weights and random seed are the same in both experiments, to ensurte that augmentation is the only difference. Experiment~1 therefore consists of 28 training runs: seven architectures, for two components, each trained with and without augmentation.

The purpose of this experiment is to measure how well the models perform in the easiest setting, where the test images come from the same facilities as the training images. The test images are taken from the same units and the same range of capture dates as the training images, and therefore share their lighting, water colour and image quality. Some test images might even share the date with development and training images, because the division into the three sets was made on the basis of the cropped images, rather than the satellite images they originate from, and a single satellite image usually contains several clarifiers and aerobic zones.

A high accuracy on this split therefore does not show that a model would work at a facility it has never seen. If the system were used to monitor other WWTW facilities, most of those facilities would not be part of the training data. A model could also learn cues that are specific to one facility or one date, such as the colour of the water at a particular facility, and still perform well on this split, since the same cues are present in the test set. The results of Experiment~1 are therefore treated as a best-case reference rather than as an estimate of how the system would perform in practice, which is the reason for Experiment~2. The difference between the two experiments gives an indication of how much performance is lost when a model is applied to a facility it was not trained on.


\section{Experiment 2: Leave-One-Facility-Out Evaluation}
\label{sec:exp_lofo}

Experiment~2 uses the leave-one-facility-out split described in Chapter~\ref{chap:systemmethods} and illustrated in Figure~\ref{fig:leave_one_out approach}. One facility is held out as the test set, and the images of the remaining facilities are divided into training and development sets in an 80/20 ratio, grouped by facility, unit and class in the same way as in Experiment~1. This is repeated until every facility has been held out once, and every repetition is referred to as a fold. The images of the test facility are never used to update the weights of the network, to calculate the class weights, to decide when training stops or to select the checkpoint that is kept. The test results of a fold are therefore an estimate of how a model would perform at a facility it has never seen.

Every architecture is trained separately for every fold, using the hyperparameters (Section~\ref{sec:exp_hyperparams}), class-weighted loss (Section~\ref{sec:exp_loss}), augmentation (Section~\ref{sec:exp_augmentation}) and training loop (Section~\ref{sec:exp_training}) described earlier in this chapter, with the same hyperparameters determined in experiment 1 used throughout. For the clarifiers, this gives five folds and 35 training runs (one for each architecture). Aerobic zones are only labelled at Atlantis, Cape Flats and Waterval (Chapter~\ref{chap:systemmethods}), so in this case there are only three aerobic zone folds and 21 training runs. Since Fisantekraal and Northern Works contribute no aerobic zone images, every aerobic zone model is trained on the two aerobic facilities that are not held out. In this experiment the folds differ considerably in size. Cape Flats contains 1476 of the 2527 clarifier images, so when it is held out, the model is trained on only 846 images, less than half of what the other folds are trained on, and tested on the largest test set. Waterval plays a similar role for the aerobic zones, with 864 of the 1743 images. The class composition of the test sets also differs between facilities. The Atlantis test set contains no \textbf{Dysfunctional} clarifiers and only three \textbf{Empty} clarifiers, and the Waterval test set contains no \textbf{Empty} clarifiers and only seven \textbf{Dysfunctional} clarifiers, while \textbf{Dysfunctional} clarifiers make up almost a third of the Northern Works test set. The recall of a class cannot be calculated at a facility where that class does not occur, and a class with only a handful of test images at a facility leads to an uncertain estimate. For the same reason, the accuracy of one fold cannot be compared directly with that of another: a model that recognises one class well and another poorly will score very differently depending on which class dominates the test set. Macro-averaged metrics, which give every class the same weight, are averaged only over the classes that occur in the test set of a fold. Otherwise, a class without any test images would count as a score of zero, and would incorrectly lower the macro average of the Atlantis and Waterval clarifier tets sets.

To summarise the performance of an architecture, the results per test fold are averaged, with every fold counting equally regardless of its size. The standard deviation across test folds is reported alongside the mean. Pooling the test images of all folds (micro-averaging) would let Cape Flats determine most of the clarifier result. The standard deviation shows how much the performance of an architecture depends on the facility it is tested on.

One part of this experiment is not fully independent of the test facility. The hyperparameters were tuned once per architecture, with Northern Works held out (Section~\ref{sec:exp_hyperparams}), and the development set of that fold contains images from the other four facilities. For the Atlantis, Cape Flats, Fisantekraal and Waterval folds, images from the test facility were therefore part of the development set on which the hyperparameters were chosen, although they were never used to train the model that is tested on them. For the aerobic zones, the tuning development set contains images from all three aerobic facilities, so this applies to every aerobic zone fold. Since only six hyperparameters were chosen in this way, the effect is likely to be small, but only the Northern Works clarifier fold is fully independent of the tuning.


\section{Experiment 3: Binary (OK / Not-OK) Reformulation}
\label{sec:exp_binary}

The multi-class models distinguish between several ways in which a component can fail, but for an operator the most important question is whether a component needs attention at all. A \textbf{Scum} clarifier classified as \textbf{Dysfunctional} is still flagged for inspection, whereas a \textbf{Scum} clarifier classified as \textbf{Functional} is missed completely. Experiment~3 therefore evaluates the models as binary classifiers, which only decide whether a component is OK or Not-OK. For the clarifiers, \textbf{Functional} is OK, and \textbf{Dysfunctional}, \textbf{Empty} and \textbf{Scum} are Not-OK. For the aerobic zones, \textbf{Functional} is OK, and \textbf{Suboptimal} and \textbf{Dysfunctional} are Not-OK.

No separate binary models are trained. Instead, the binary decision is derived from the multi-class models of Experiments~1 and~2. The Not-OK score of an image is the total probability that the model assigns to the Not-OK classes,

\begin{equation}
    s = 1 - P(\mathrm{Functional}),
\end{equation}

and the image is classified as Not-OK when $s \geq t$, for a threshold $t$. The binary results therefore come from exactly the same models as the multi-class results, so the two can be compared directly, and no additional training runs are needed. A model used in this way also still predicts a specific class for every component it flags.

With Not-OK treated as the positive class, the recall (or sensitivity) is the fraction of Not-OK components that are flagged, and the specificity is the fraction of OK components that are correctly left unflagged. The two kinds of mistake do not have the same cost. A false alarm only costs an operator the time to look at the image, while a missed Not-OK component may go unnoticed until the next satellite image of the facility becomes available. The threshold is therefore not left at a default value, but is chosen so that the recall of the Not-OK class reaches a target of 95\%. The recall is evaluated at 500 evenly spaced thresholds between 0 and 1, and the largest threshold that still reaches the target is selected, since this is the threshold that raises the fewest false alarms while meeting it. For Experiment~2, one threshold is chosen per architecture and shared by all of its folds: the recall is calculated separately for every held-out facility, and the largest threshold at which the mean recall across facilities reaches 95\% is selected.

The ROC curve and its AUC are also calculated for the binary problem, since they describe the trade-off between recall and specificity over all thresholds rather than at a single one. For Experiment~2, a separate ROC curve is calculated for every held-out facility. These curves are interpolated onto a common set of false positive rates and averaged, and the AUC is reported as the mean and standard deviation across facilities. The test images of all facilities are not pooled into a single curve, because Cape Flats would then dominate the result, and because the scores in each fold come from a different model. In the same way, the binary confusion matrix at the chosen threshold is normalised per row, so that it shows rates rather than counts, and then averaged across facilities.

Since the threshold is chosen on the test predictions themselves, the recall at the chosen threshold is not an independent result. It is at least 95\% by construction on the stratified split, and at least 95\% on average across facilities for the leave-one-facility-out split. What this experiment measures is the specificity that has to be given up to reach this recall and, for the leave-one-facility-out split, how much the recall at one shared threshold varies from one facility to the next. The recall at the shared threshold is therefore also reported for every held-out facility separately. In practice, the threshold would have to be fixed before the system is used at a new facility, so a large spread between facilities would mean that a threshold chosen on known facilities cannot be relied on to reach the target recall at a new one.


\section{Evaluation Metrics}
\label{sec:exp_metrics}

Every run is evaluated once on its test set, after training has finished and the checkpoint with the lowest development loss has been restored (Section~\ref{sec:exp_training}). The predicted class of a test image is the class with the highest softmax probability, and the following metrics are calculated from these predictions and probabilities.

\textbf{Accuracy} is the fraction of test images whose predicted class is correct. It is the simplest summary of a run, but it is dominated by the common classes: a model that recognises \textbf{Functional} and \textbf{Scum} clarifiers well can reach a high accuracy while missing most of the rare \textbf{Empty} clarifiers. As discussed in Section~\ref{sec:exp_lofo}, the accuracy of one fold can also not be compared directly with that of another, since the class composition of the test sets differs between facilities.

\textbf{Precision, recall and F1 score} are therefore also calculated for every class separately. With $TP_c$, $FP_c$ and $FN_c$ the number of true positives, false positives and false negatives for class $c$,

\begin{equation}
    \mathrm{Precision}_c = \frac{TP_c}{TP_c + FP_c}, \qquad
    \mathrm{Recall}_c = \frac{TP_c}{TP_c + FN_c},
\end{equation}
\begin{equation}
    F1_c = \frac{2 \cdot \mathrm{Precision}_c \cdot \mathrm{Recall}_c}{\mathrm{Precision}_c + \mathrm{Recall}_c}.
\end{equation}

Precision is the fraction of images predicted as class $c$ that really belong to it, and recall is the fraction of the images of class $c$ that the model finds. The F1 score is their harmonic mean, which is only high when both are high. To summarise a run in a single number that gives every class the same weight, the per-class values are averaged into macro-averaged precision, recall and F1 scores. As explained in Section~\ref{sec:exp_lofo}, this average only includes the classes that occur in the test set.

The \textbf{confusion matrix} of every run counts, for every true class, how many of its test images were assigned to each predicted class. It shows not only how many images are misclassified, but also which classes are mistaken for each other, which is what the Grad-CAM analysis in Section~\ref{sec:results_gradcam} builds on.

The \textbf{area under the ROC curve (AUC)} measures how well the softmax probabilities separate the classes, independently of any single decision rule. For every class, a one-vs-rest ROC curve is calculated from the predicted probability of that class, by plotting the true positive rate against the false positive rate as the decision threshold is varied. An AUC of 1 means that every image of the class receives a higher probability than every other image, while 0.5 corresponds to random guessing. The mean AUC of a run is the average over the classes that occur in its test set, since the ROC curve of a class without test images is undefined. The binary OK / Not-OK AUC of Experiment~3 is calculated in the same way from the Not-OK score (Section~\ref{sec:exp_binary}).

\textbf{Loss and accuracy curves} record the training and development loss and accuracy after every epoch of a run, with the epoch of the restored checkpoint marked. They are not used to compare architectures, but show whether a run converged, when it started to overfit, and whether early stopping ended it at a sensible point.

Of these metrics, recall is the most important in the context of this project. The system is meant to flag components that are not working properly, so that an operator can inspect them. A component with low recall for a failure class, such as a \textbf{Dysfunctional} clarifier or a \textbf{Suboptimal} aerobic zone, would be missed and could go unnoticed until the next satellite image of the facility, whereas a false positive only costs an operator the time to look at an image. For this reason, the recall of the failure classes is reported alongside the macro-averaged scores, and the operating point in Experiment~3 is chosen to reach a target recall rather than the highest accuracy.


\section{Qualitative Analysis: Grad-CAM}
\label{sec:exp_gradcam}

Accuracy does not show what in an image a model bases its prediction on, so a model could rely on something unrelated to the state of the component, such as the water colour at a particular facility or the rim of a clarifier. Grad-CAM~\citep{selvaraju2017gradcam} is used to check this, by highlighting the regions of an image that contributed the most to a prediction.

\subsection{Method}
\label{subsec:gradcam_method}

Grad-CAM uses the feature maps $A^k$ of the last convolutional layer. Each feature map is weighted by the gradient of the score $y^c$ of class $c$ (before the softmax) with respect to that map, averaged over all $Z$ positions:

\begin{equation}
    \alpha_k^c = \frac{1}{Z} \sum_{i} \sum_{j} \frac{\partial y^c}{\partial A^k_{ij}}.
    \label{eq:gradcam_weights}
\end{equation}

The weighted feature maps are then summed, and only the positive contributions are kept:

\begin{equation}
    L^c = \mathrm{ReLU}\left( \sum_{k} \alpha_k^c A^k \right).
    \label{eq:gradcam_map}
\end{equation}

$L^c$ is resized to the input image and drawn over it as a heatmap, where red regions contributed the most to the prediction. Every map is scaled separately, so the colours cannot be compared between images. The \texttt{pytorch-grad-cam} library~\citep{gildenblat2021pytorchcam} was used for the implementation.

\subsection{Models and Example Selection}
\label{subsec:gradcam_setup}

For each component, the architecture with the highest mean macro-averaged F1 score in the leave-one-facility-out experiment (Section~\ref{sec:exp_lofo}) was analysed, on the facility that was held out in one of its folds. For the clarifiers, Fisantekraal was used, since it contains all four clarifier classes, and for the aerobic zones, Waterval was used, since it has the most aerobic zone images. For each class, one correctly classified image was chosen at random, along with one image from each of the most common mistakes. The heatmaps are calculated for the predicted class, so for a mistake they show what the model took as evidence for the wrong class.
