\section{Hyperparameter Tuning}
\label{sec:exp_hyperparams}
Some of the parameters were fixed, and is the same for every one of the six architectures. These values were never changed, either because a well-established default already exists or because there was no reason to expect the best value to depend on the architecture. This covers Adam's $\beta_2$ term (kept at $0.9$, the default recommended in Adam's original paper and rarely changed in practice), the $L_2$ weight decay ($10^{-4}$, a standard mild regularisation strength), and the training loop's own settings: a maximum of 100 epochs, an early-stopping patience of 10 epochs, and a fixed random seed of 42.

Some parameters were tuned automatically, but only for three architectures: ResNet-50, DenseNet-121, and Inception-v3. This tuning was carried out earlier in the project, under the original mixed-facility split (Section~\ref{sec:exp_mixed}), in two stages. The first stage was a grid search over the classifier head itself: for a small set of candidate values of $H$ (hidden layers) and $N$ (neurons per layer), each combination was trained and evaluated, and the combination with the best validation accuracy was kept (Table~\ref{tab:arch_grid_search}). The second stage, with the head now fixed, was a Bayesian optimisation search over the remaining training hyperparameters: learning rate, Adam's $\beta_1$, the step size of the learning rate schedule, and batch size (Table~\ref{tab:bayes_opt}). Unlike a grid search, Bayesian optimisation does not try every combination in a fixed grid; it uses the results of earlier trials to decide which combination is likely to be worth trying next, which finds a good setting in far fewer trials.

One result of that search is worth calling out directly: for DenseNet-121 and Inception-v3, the optimal $\beta_1$ found was effectively zero. Since $\beta_1$ controls how much Adam smooths the gradient direction from one step to the next (its momentum term), a value of zero means each step is based almost entirely on the current batch's gradient, with very little memory of previous steps, which the search found worked better for these two architectures than the conventional default of $0.9$.

The third group was chosen by hand, for the remaining three architectures. ResNet-18 is deliberately kept as an untuned baseline (Section~\ref{sec:exp_architectures}): it uses the simplest possible head (no hidden layers) and a standard default Adam learning rate, rather than anything found by search. EfficientNet-B0 and ConvNeXt-Tiny were added to the project after the tuning sweep above had already been completed, so instead of repeating the search, they were given sensible, manually-chosen values that broadly follow the pattern the search found for the other three architectures. Table~\ref{tab:full_hyperparams} brings all three groups together into the single configuration actually used to train each architecture.

\section{Training Procedure}
\label{sec:exp_training}

Every architecture is trained with the same underlying procedure; only the specific numbers (learning rate, batch size, and so on) change per architecture, as set out in Section~\ref{sec:exp_hyperparams}. All six use the Adam optimiser, which adjusts each parameter's effective learning rate individually based on that parameter's recent gradient history, rather than applying one fixed step size to every weight in the network. Its two smoothing terms, $\beta_1$ and $\beta_2$, control how much of that history it remembers: $\beta_1$ is tuned per architecture, while $\beta_2$ is left at the common default of $0.9$ for all six. A small $L_2$ weight penalty ($10^{-4}$, applied equally to every architecture) is added on top, gently discouraging any single weight from growing large purely to fit noise in the training set.

Rather than using one fixed learning rate for an entire run, the learning rate is reduced as training progresses, since large steps are useful early on to make fast progress but become counter-productive once the model is close to a good solution, where they cause it to overshoot instead of settling in. The ResNet-18 baseline uses \texttt{ReduceLROnPlateau}: it watches validation loss directly and halves the learning rate whenever three consecutive epochs pass with no improvement. Every other architecture instead uses the simpler, pre-scheduled \texttt{StepLR}: the learning rate is cut by a factor of ten after a fixed, architecture-specific number of epochs. This difference is mostly a historical artefact of when each architecture was added to the project rather than a deliberate design choice, and is worth flagging as such.

Training is allowed to run for up to 100 epochs, but is stopped early if validation loss has not improved for 10 consecutive epochs, since the point at which a given architecture stops improving and starts overfitting is not known ahead of time and differs from one architecture to the next. Validation \emph{loss}, rather than accuracy, is used to decide both when to stop and which epoch's weights to keep. Whichever epoch achieved the lowest validation loss is the one whose weights are restored and carried forward to testing, rather than simply whatever weights training happened to end on.

Two further techniques are used purely to make training computationally feasible, rather than to change what is learned. First, training runs in mixed precision on GPU: most computations use 16-bit rather than 32-bit floating point, roughly halving memory use and increasing throughput, with a loss-scaling step included to prevent the smaller numerical range of 16-bit floats from rounding small gradients to zero. Second, some of the batch sizes in Table~\ref{tab:full_hyperparams} (e.g.\ 121 images for ResNet-50) are too large to fit in GPU memory at once alongside a deep network's activations. Rather than shrinking the batch size and drifting away from the tuned value, training instead processes several smaller "micro-batches" in sequence, accumulating their gradients, and only updates the network's weights once enough micro-batches have been seen to match the intended batch size: mathematically equivalent to using the full batch size directly, just spread over several smaller forward and backward passes instead of one large one.

Inception-v3 is trained with one additional detail: during training only, it produces a second, auxiliary prediction partway through the network, and the loss from this auxiliary output is added to the main loss at a reduced weight of $0.4$. This gives the earlier layers of the network a more direct training signal than would otherwise reach them through such a deep network, and is discarded entirely once training finishes, playing no role in the model's actual predictions at test time.

Finally, a fixed random seed (42) is used throughout, covering not only the dataset shuffling and splitting already described in Chapter~\ref{chap:systemmethods} but also the random initialisation of each architecture's new classifier head, so that a given experiment can be reproduced exactly if re-run.
