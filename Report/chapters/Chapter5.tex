\section{Overview}
\label{sec:exp_overview}

This chapter describes how the classification system was designed and configured, and which experiments were run with it. The clarifiers and the aerobic zones are treated as two separate classification problems (Chapter~\ref{chap:systemmethods}), but both are handled by the same system, and every experiment is carried out for both components unless stated otherwise. The first part covers the parts of the system that are shared by every experiment: the model architectures and how transfer learning is applied to them (Section~\ref{sec:exp_architectures}), the augmentations applied to the training images (Section~\ref{sec:exp_augmentation}), how the class imbalance in the dataset is handled (Section~\ref{sec:exp_loss}), how the hyperparameters of each architecture were chosen (Section~\ref{sec:exp_hyperparams}), and the training loop itself (Section~\ref{sec:exp_training}).

The second part describes the three experiments that were carried out using this system:

\begin{enumerate}
    \item \textbf{Mixed-facility baseline} (Section~\ref{sec:exp_mixed}): the images of all five facilities are pooled and divided using the chronological split described in Chapter~\ref{chap:systemmethods}, in which every image captured from January 2020 onwards is a test image.
    \item \textbf{Leave-one-facility-out evaluation} (Section~\ref{sec:exp_lofo}): each facility is held out in turn as an unseen test facility, while the model is trained on the remaining facilities, with part of them held out as a development set. This gives five folds for the clarifiers, and three for the aerobic zones, which are only labelled at three facilities. This experiment estimates how well a model would perform on a facility it has never seen before.
    \item \textbf{Binary (OK / Not-OK) approach} (Section~\ref{sec:exp_binary}): the classes are collapsed into a two-class problem, where \textbf{Functional} is treated as OK and every other class is treated as Not-OK: \textbf{Dysfunctional}, \textbf{Empty} and \textbf{Scum} for the clarifiers, and \textbf{Suboptimal} and \textbf{Dysfunctional} for the aerobic zones.
\end{enumerate}

The chapter ends with the metrics used to evaluate every run (Section~\ref{sec:exp_metrics}) and the Grad-CAM method used to inspect which parts of an image a model bases its classification on (Section~\ref{sec:exp_gradcam}).

Figure~\ref{fig:experimental_pipeline} summarises the pipeline from start to finish. It starts from the labelled satellite images described in Chapter~\ref{chap:systemmethods}, which \texttt{prep.py} crops into individual images sorted into one folder per class. These images are then divided into training, development and test sets, either with the chronological split of Experiment~1 or by facility, so that no image from the held-out test facility is ever used during training. Every image is resized and normalised before it is passed to the network, and images in the training set are also randomly augmented (Section~\ref{sec:exp_augmentation}). Each file contains the test metrics, the confusion matrix, the training history and the classification made for every test image.


\section{Model Architectures and Transfer Learning}\label{sec:exp_architectures}

Four CNN architectures are compared in this project: ResNet-18 (Section~\ref{sec:resnet}), DenseNet-121 (Section~\ref{sec:densenet}), EfficientNet-B0 (Section~\ref{sec:efficientnet}) and ConvNeXt-Tiny (Section~\ref{sec:convnext}). ResNet-18 is trained twice, once fine-tuned from ImageNet weights and once from randomly initialised weights, which gives five models. Table~\ref{tab:arch_sizes} lists the sizes of the architectures, which range from 5.3 to 28.6 million parameters. All four are taken from the torchvision library \citep{torchvision2016}, and the same five models are trained for both the clarifiers and the aerobic zones.

The ResNet-50~\citep{he2016resnet} and Inception-v3~\citep{szegedy2016inception} architectures were also included in this evaluation. However, neither had the highest macro F1 score for either component in either experiment, and due to space restrictions in this report, they are not reported on.

The ResNet-18 trained from randomly initialised weights is referred to as ResNet-18 (scratch). It is not tuned, and uses one fixed set of default hyperparameters (Section~\ref{subsec:defaults}). It was added to the project to measure the effect of pretraining, that is, whether the pretrained architectures outperform the same architecture trained only on this project's own, small dataset.

For each of the four pretrained architectures, transfer learning follows the same recipe. The architecture's convolutional backbone is loaded with weights pretrained on ImageNet~\citep{deng2009imagenet, russakovsky2015imagenet}, specifically torchvision's \texttt{IMAGENET1K\_V1} weights. Its original 1000-class ImageNet output layer is then discarded, and a new classifier head, sized by that architecture's own tuned hidden layers ($H$) and neurons ($N$) (Section~\ref{sec:exp_hyperparams}), is put in its place: a stack of $H$ \texttt{Linear+ReLU} pairs followed by a final \texttt{Linear} layer mapping to the project's number of classes. Every parameter in the network, backbone included, is then fine-tuned on the WWTW dataset. No layers are frozen, so pretraining only supplies a starting point for every weight rather than fixing any of them in place.

Every one of these architectures ends in the same kind of structure: a convolutional backbone feeding into one or more fully connected layers that produce the 1000 ImageNet class scores. Replacing this final part therefore means locating whichever attribute of the model object torchvision happens to store it under, which differs from one architecture's implementation to the next. For ResNet-18, it is a single attribute named \texttt{model.fc}. DenseNet-121 stores the same kind of single layer under \texttt{model.classifier} instead, which is simply a difference in torchvision's naming convention rather than an architectural difference. For EfficientNet-B0 and ConvNeXt-Tiny, \texttt{model.classifier} is itself a short stack of several layers rather than a single one, so only the specific layer within it that produces the final class scores, the last \texttt{Linear} layer, is replaced, and everything before it is left as it was. In practice, this means EfficientNet-B0 keeps the dropout layer that is located just before the original output layer.

One architecture needs one further, architecture-specific adjustment. ConvNeXt-Tiny's global average pooling layer is replaced with global max pooling, so the feature vector reaching its classifier head is composed of each channel's strongest activation rather than its average.

Every image is resized to a fixed input size before it is passed to the network, without changing its aspect ratio: the image is scaled until it fits inside the input size, and the remaining area is filled with black, with the image centred. The clarifier crops are close to square, since they are cut around a circular tank, and use an input size of $224\times224$ pixels. The aerobic zones are wide rectangles, with a median width of about 2.6 times their height, and use an input size of $112\times224$ pixels (height $\times$ width), so black bars are added above and below most of them. After resizing, every image is normalised with the mean and standard deviation of the ImageNet images, per colour channel, since the pretrained backbones were trained on inputs normalised in this way.


\section{Augmentation}
\label{sec:exp_augmentation}

Data augmentation makes small, random changes to the training images, so that the network sees a slightly different version of every image each time it is used. This increases the variety in the training data without collecting any new images, and makes it harder for the network to memorise individual images. Augmentation is applied to the training set only. The development and test images are never augmented, so that they are evaluated exactly as they are.

The augmentations are applied by PyTorch \citep{paszke2019pytorch} each time an image is loaded, rather than being generated once and saved to disk. The size of the training set therefore stays the same, but every epoch sees a new, randomly augmented version of each training image. Three augmentations are applied, in the following order:

\begin{itemize}
    \item \textbf{Horizontal flip}: the image is mirrored from left to right with a probability of 50\%.
    \item \textbf{Rotation}: the image is rotated by a random angle, chosen uniformly between $-15^\circ$ and $+15^\circ$. The output image keeps its original size, so the corners that are rotated out of the frame are cut off, and the empty corners that are rotated into the frame are filled with black.
    \item \textbf{Colour jitter}: the brightness, contrast, saturation and hue of the image are changed by a random amount, with the four adjustments applied in a random order. The brightness and contrast are each multiplied by a random factor between $0.6$ and $1.4$, the saturation by a random factor between $0.7$ and $1.3$, and the hue is shifted by up to $\pm 0.1$ of the full colour wheel (at most $36^\circ$).
\end{itemize}

The flip and rotation are suited to this dataset because the images are taken from directly above. A clarifier seen from above has no fixed orientation, so a mirrored or slightly rotated clarifier is still a realistic example of the same class. When \texttt{prep.py} crops a clarifier, it also sets every pixel outside the annotated circle to black, which matches the black corners introduced by the rotation. The aerobic zones are not masked, since their annotations are rectangles, but have black bars above and below them from the resizing (Section~\ref{sec:exp_architectures}). For them, a rotation cuts off the ends of the zone and adds small black triangles along its edges. The rotation is limited to $\pm 15^\circ$, so most of the surface of the zone remains visible.

The colour jitter targets a different problem. The images come from different facilities and were captured on different dates, so the lighting, sun glare and water colour vary between images. The colour jitter is intended to stop the network from memorising the exact colour or brightness of the water at a particular facility, and to make it rely on other features of the clarifier instead.

Figure~\ref{fig:augmentation_examples} shows these augmentations applied to a single training image. The top row shows each augmentation on its own, while the bottom row shows four randomly chosen outputs of the full augmentation pipeline, as the network would see them during training.

\section{Class Imbalance}
\label{sec:exp_loss}

As shown in Tables~\ref{tab:aerobic_summary} and~\ref{tab:clarifier_summary} in Section~\ref{sec:final_dataset}, the classes of both components are highly imbalanced. For the clarifiers, \textbf{Functional} and \textbf{Scum} clarifiers make up most of the dataset (2090 of the 2527 images), while \textbf{Dysfunctional} and especially \textbf{Empty} clarifiers are much less common. For the aerobic zones, \textbf{Suboptimal} is the rare class, with only 223 of the 1743 images. If every image contributes equally to the loss, the network can reach a low loss by mostly assigning images to the common classes, and has little incentive to learn the rare ones.

To counter this, the cross-entropy loss is weighted per class, so that the network is penalised more for misclassifying an image from a rare class than from a common one. The weight of each class is inversely proportional to the number of training images in that class, and the weights are then normalised so that they sum to the number of classes. For $K$ classes, where $n_c$ is the number of training images in class $c$, the weight of class $c$ is

\begin{equation}
    w_c = K \cdot \frac{1/n_c}{\sum_{j=1}^{K} 1/n_j}.
\end{equation}

A class with average representation therefore gets a weight close to one, a rare class gets a weight larger than one, and a common class gets a weight smaller than one. These weights are passed to PyTorch's \texttt{CrossEntropyLoss}, which multiplies the loss of each image by the weight of its true class, and divides the sum over a batch by the sum of these weights rather than by the number of images. The training data itself is not resampled, so every training image is still used exactly once per epoch.

The weights are calculated from the training set only, and are recalculated for every split, since the class counts change depending on which facility is held out. For the clarifiers, the Cape Flats split stands out. Cape Flats contains 120 of the 145 \textbf{Empty} clarifiers in the dataset (Table~\ref{tab:clarifier_summary} in Section~\ref{sec:final_dataset}), so when it is held out for testing, only 25 \textbf{Empty} images are left, 21 of which are in the training set. The weight of the \textbf{Empty} class rises to 3.09 as a result, about twenty times the weight of the \textbf{Scum} class (0.15). In the same way, Northern Works contains 131 of the 292 \textbf{Dysfunctional} clarifiers, so holding it out raises the \textbf{Dysfunctional} weight to 1.55, compared with about 1.1 in the Atlantis, Fisantekraal and Waterval splits.

For the aerobic zones, \textbf{Suboptimal} has the highest weight in every split, between 1.48 and 1.89. The held-out facility again changes the weights of the other two classes. Waterval contains 543 of the 707 \textbf{Functional} aerobic zones, so when it is held out, \textbf{Functional} becomes a minority class in the training set, with a weight of 1.19 compared with 0.34 to 0.68 in the other splits. The Waterval test set is therefore dominated by a class that is comparatively scarce in its own training set. Similarly, Cape Flats contains 562 of the 813 \textbf{Dysfunctional} aerobic zones, and holding it out raises the \textbf{Dysfunctional} weight to 0.82, compared with 0.34 to 0.53 in the other splits.

The same weighted loss is also used to calculate the development loss. Since the development loss decides when training stops early and which epoch's weights are kept (Section~\ref{sec:exp_training}), the class weighting also influences model selection, and not only the gradient updates during training.


\section{Hyperparameter Tuning}
\label{sec:exp_hyperparams}

Some hyperparameters were fixed for every architecture: Adam's $\beta_2$ ($0.999$, the default from Adam's original paper \citep{kingma2015adam}), the $L_2$ weight decay ($10^{-4}$), a maximum of 100 epochs, an early-stopping patience of 10 epochs and a random seed of 42. The remaining hyperparameters, namely the number of hidden layers $H$ and neurons per layer $N$ of the classifier head, the learning rate, Adam's $\beta_1$, the \texttt{StepLR} step size and the batch size, were tuned with Optuna~\citep{akiba2019optuna}, a hyperparameter optimisation library. This was done for the four pretrained models, separately for the clarifiers and the aerobic zones, giving eight searches. ResNet-18 (scratch) was not tuned (Section~\ref{subsec:defaults}).

\subsection{Why Optuna}
\label{subsec:why_optuna}

The six tuned hyperparameters interact, so tuning them one at a time can miss good combinations, and a grid search over all six is too expensive. Optuna searches all six jointly with a Tree-structured Parzen Estimator (TPE) sampler \citep{bergstra2011tpe}, which samples new candidates from the regions of the search space where earlier trials scored well. A \texttt{MedianPruner} also stops a trial early if its development accuracy falls below the median of the earlier trials at the same epoch.

\subsection{Search Procedure}
\label{subsec:search_procedure}

The first ten trials of every search are sampled at random, and the last ten are guided by TPE. The pruner only becomes active after five trials have completed, and does not prune a trial before its fifth epoch. Every trial uses the same training loop as the final models (Section~\ref{sec:exp_training}) and is scored by its development accuracy at the epoch with the lowest development loss, which is the checkpoint that is kept when a model is trained.

To limit the compute cost, each search was run once rather than on every fold: on the leave-one-facility-out fold with Northern Works held out for the clarifiers, and with Atlantis held out for the aerobic zones, since Northern Works has no aerobic zones. The selected values are used for every fold and for the chronological split (Sections~\ref{sec:exp_mixed} and~\ref{sec:exp_lofo}).

\subsection{ResNet-18 (Scratch)}
\label{subsec:defaults}

ResNet-18 (scratch) is trained from randomly initialised weights rather than fine-tuned (Section~\ref{sec:exp_architectures}). It was not included in the search, and uses the same default values for both components (Table~\ref{tab:hyperparams}): three hidden layers of 1024 neurons, a learning rate of $10^{-4}$, Adam's default $\beta_1$ of $0.9$, a step size of 15 and a batch size of 32. It is trained with the same loop and early stopping as the other models (Section~\ref{sec:exp_training}). Since its hyperparameters also differ from those of the pretrained ResNet-18, the difference between the two models includes the effect of tuning as well as that of pretraining.


\section{Training Procedure}
\label{sec:exp_training}

Every architecture is trained with the same procedure; only the specific hyperparameter values are different, as set out in Section~\ref{sec:exp_hyperparams}. 

Rather than using one fixed learning rate for an entire run, every architecture uses \texttt{StepLR} to cut the learning rate by a factor of ten every time a fixed, architecture-specific number of epochs (the step size) has passed (Section~\ref{sec:exp_hyperparams}), since large steps are useful early on to make fast progress but become counter-productive once the model is close to a good solution, where they cause it to overshoot instead of converging.

Training is allowed to run for up to 100 epochs, but is stopped early if development loss has not improved for 10 consecutive epochs, since the point at which a given architecture stops improving and starts overfitting is not known ahead of time and differs from one architecture to the next. Development \emph{loss}, rather than accuracy, is used to decide both when to stop and which epoch's weights to keep: whichever epoch achieved the lowest development loss is the one whose weights are restored and carried forward to testing, rather than simply whatever weights training happened to end on. Figure~\ref{fig:training_flow} summarises this loop.

The same fixed seed used throughout this project (Section~\ref{sec:exp_hyperparams}) also covers the random initialisation of each architecture's new classifier head and the order in which the training images are shuffled, in addition to the dataset splitting described in Chapter~\ref{chap:systemmethods}. A repeated run therefore starts from the same weights and splits. It is not guaranteed to reproduce the results exactly, however, since some GPU operations are not deterministic and mixed precision adds small rounding differences, so repeated runs can differ slightly.


\section{Experiment 1: Mixed-Facility Baseline}
\label{sec:exp_mixed}

The first experiment does not take into account which facility an image comes from. The images of all five facilities are pooled and divided into training, development and test sets using the chronological split described in Chapter~\ref{chap:systemmethods}. Every image captured from January 2020 onwards is a test image. The images captured before January 2020 are grouped by facility, unit and class, each group is shuffled using the fixed random seed of 42, and the group is then divided in an 80/20 ratio into training and development images. All five models are trained using this division of the data, for both the clarifiers and the aerobic zones, with the hyperparameter values in Table~\ref{tab:hyperparams} (Section~\ref{sec:exp_hyperparams}). Experiment~1 is also used to measure the effect of augmentation. Every model is trained a second time on the same data but without augmentation (resizing and normalisation is maintained for all train, development and test images). The data, hyperparameters, class weights and random seed are the same in both experiments, to ensure that augmentation is the only difference. Experiment~1 therefore consists of 20 training runs: five models, for two components, each trained with and without augmentation. The results are given in Appendix~\ref{sec:results_augmentation}.

The purpose of this experiment is to estimate how well the models perform at facilities whose earlier images are part of the training data. This is the usual situation in the intended use of the system (Chapter~\ref{chap:introduction}): new images of a facility are classified, an operator relabels the flagged images, and the relabelled images are added to the training data. Since a satellite image has a single capture date, no test image comes from the same satellite image as a training or development image.

A model could also learn cues that are specific to one facility, such as the colour of the water at that facility, and still perform well on this split, since the same cues are present in the test set. The results of Experiment~1 therefore do not show how a model would perform at a facility it has never seen, which is the reason for Experiment~2. The difference between the two experiments gives an indication of how much performance is lost when a model is applied to a facility it was not trained on.


\section{Experiment 2: Leave-One-Facility-Out Evaluation}
\label{sec:exp_lofo}

Experiment~2 uses the leave-one-facility-out split described in Chapter~\ref{chap:systemmethods} and illustrated in Figure~\ref{fig:leave_one_out approach}. One facility is held out as the test set, and the images of the remaining facilities are divided into training and development sets in an 80/20 ratio, grouped by facility, unit and class in the same way as in Experiment~1. This is repeated until every facility has been held out once, and every repetition is referred to as a fold. The images of the test facility are never used to update the weights of the network, to calculate the class weights, to decide when training stops or to select the checkpoint that is kept. The test results of a fold are therefore an estimate of how a model would perform at a facility it has never seen.

Every architecture is trained separately for every fold, using the hyperparameters (Section~\ref{sec:exp_hyperparams}), class-weighted loss (Section~\ref{sec:exp_loss}), augmentation (Section~\ref{sec:exp_augmentation}) and training loop (Section~\ref{sec:exp_training}) described earlier in this chapter, with the same hyperparameters used throughout. For the clarifiers, this gives five folds and 25 training runs (one for each model and fold). Aerobic zones are only labelled at Atlantis, Cape Flats and Waterval (Chapter~\ref{chap:systemmethods}), so in this case there are only three aerobic zone folds and 15 training runs. Since Fisantekraal and Northern Works contribute no aerobic zone images, every aerobic zone model is trained on the two aerobic facilities that are not held out. In this experiment the folds differ considerably in size. Cape Flats contains 1476 of the 2527 clarifier images, so when it is held out, the model is trained on only 846 images, less than half of what the other folds are trained on, and tested on the largest test set. Waterval plays a similar role for the aerobic zones, with 864 of the 1743 images. The class composition of the test sets also differs between facilities. The Atlantis test set contains no \textbf{Dysfunctional} clarifiers and only three \textbf{Empty} clarifiers, and the Waterval test set contains no \textbf{Empty} clarifiers and only seven \textbf{Dysfunctional} clarifiers, while \textbf{Dysfunctional} clarifiers make up almost a third of the Northern Works test set. The recall of a class cannot be calculated at a facility where that class does not occur, and a class with only a handful of test images at a facility leads to an uncertain estimate. For the same reason, the accuracy of one fold cannot be compared directly with that of another: a model that recognises one class well and another poorly will score very differently depending on which class dominates the test set. Macro-averaged metrics, which give every class the same weight, are averaged only over the classes that occur in the test set of a fold. Otherwise, a class without any test images would count as a score of zero, and would incorrectly lower the macro average of the Atlantis and Waterval clarifier tets sets.

To summarise the performance of an architecture, the results per test fold are averaged, with every fold counting equally regardless of its size. The standard deviation across test folds is reported alongside the mean. Pooling the test images of all folds (micro-averaging) would let Cape Flats determine most of the clarifier result. The standard deviation shows how much the performance of an architecture depends on the facility it is tested on.

One part of this experiment is not fully independent of the test facility. The hyperparameters were tuned once per architecture, with Northern Works held out for the clarifiers and Atlantis held out for the aerobic zones (Section~\ref{sec:exp_hyperparams}), and the development set of that fold contains images from the other facilities. For the other folds, images from the test facility were therefore part of the development set on which the hyperparameters were chosen, although they were never used to train the model that is tested on them. Since only six hyperparameters were chosen in this way, the effect is likely to be small, but only the Northern Works clarifier fold and the Atlantis aerobic zone fold are fully independent of the tuning.


\section{Experiment 3: Binary (OK / Not-OK) Reformulation}
\label{sec:exp_binary}

The multi-class models distinguish between several ways in which a component can fail, but for an operator the most important question is whether a component needs attention or not. A \textbf{Scum} clarifier classified as \textbf{Dysfunctional} is still flagged for inspection, whereas a \textbf{Scum} clarifier classified as \textbf{Functional} is missed completely. Experiment~3 therefore evaluates the models as binary classifiers, which only decide whether a component is functioning correctly (OK) or not (Not-OK). For the clarifiers, \textbf{Functional} means OK, while \textbf{Dysfunctional}, \textbf{Empty} and \textbf{Scum} are Not-OK. For the aerobic zones, \textbf{Functional} means OK, while \textbf{Suboptimal} and \textbf{Dysfunctional} are Not-OK.

No separate binary models are trained. Instead, the binary decision is derived from the multi-class models of Experiments~1 and~2. The Not-OK score of an image is the total probability that the model assigns to the Not-OK classes,

\begin{equation}
    s = 1 - P(\mathrm{Functional}),
\end{equation}

and the image is classified as Not-OK when $s \geq t$, for a threshold $t$. The binary results therefore come from exactly the same models as the multi-class results, so the two can be compared directly. The binary evaluation is carried out on both the chronological split of Experiment~1 and the leave-one-facility-out split of Experiment~2.

With Not-OK treated as the positive class, the recall (or sensitivity) is the fraction of Not-OK components that are flagged as such, while the specificity is the fraction of OK components that are correctly left unflagged. These two kinds of mistake do not have the same cost. A false alarm only costs an operator the time to look at the image and make his or her own confirmatory assessment, while a missed Not-OK component may go unnoticed until the next satellite image of the facility becomes available. The decision threshold therefore must be chosen so that the recall of the Not-OK class reaches a target of 95\% on the development set of the same run. The recall is evaluated at 500 evenly spaced thresholds between 0 and 1, and the largest threshold that still reaches the target is selected, since this is the threshold that also raises the fewest false alarms. The recall, specificity and precision are then calculated on the test set at this threshold. For the leave-one-facility-out models of Experiment~2, every fold has its own threshold, chosen on the development set of that fold, which contains no images of the held-out facility.

The ROC curve and its AUC are also calculated for the binary problem, since they describe the trade-off between recall and specificity over all thresholds rather than at a single one. For the leave-one-facility-out models, the binary results are summarised across held-out facilities in the same way as the multi-class results (Section~\ref{sec:exp_lofo}). The ROC curve of every fold is interpolated onto a common set of false positive rates before the curves are averaged, and the binary confusion matrix at the chosen threshold is normalised per row, so that it shows rates rather than counts, before it is averaged.

Since the test set plays no part in choosing the threshold, the test recall can be lower or higher than 95\%. The development set is also used to select the checkpoint (Section~\ref{sec:exp_training}), so the development recall may be slightly optimistic. For the leave-one-facility-out split, the test recall is also reported for every held-out facility separately. In practice, the threshold would have to be fixed before the system is used at a new facility, so a test recall well below 95\% at some facilities would mean that a threshold chosen on known facilities cannot be relied on to reach the target recall at a new one.


\section{Evaluation Metrics}
\label{sec:exp_metrics}

Every run is evaluated once on its test set, after training has finished and the checkpoint with the lowest development loss has been restored (Section~\ref{sec:exp_training}). A test image is assigned to the class with the highest softmax probability, and the metrics described in Section~\ref{sec:metrics_background} are calculated from these classifications and probabilities.

Of these metrics, recall is the most important in the context of this project. The system is meant to flag components that are not working properly, so that an operator can inspect them. A component with low recall for a failure class, such as a \textbf{Dysfunctional} clarifier or a \textbf{Suboptimal} aerobic zone, would be missed and could go unnoticed until the next satellite image of the facility, whereas a false positive only costs an operator the time to look at an image. For this reason, the recall of the failure classes is reported alongside the macro-averaged scores, and the operating point in Experiment~3 is chosen to reach a target recall rather than the highest accuracy.


\section{Qualitative Analysis: Grad-CAM}
\label{sec:exp_gradcam}

Classification performance alone does not show what in an image a model bases its decision on, so a model could rely on something unrelated to the state of the component, such as the water colour at a particular facility or the rim of a clarifier. Grad-CAM (Section~\ref{sec:gradcam_background}) is used to check this, by highlighting the regions of an image that contributed the most to a classification.

\subsection{Method}
\label{subsec:gradcam_method}

Grad-CAM was applied to the output of the last feature block of each selected model, using the \texttt{pytorch-grad-cam} library~\citep{gildenblat2021pytorchcam}. The heatmaps are superimposed on the input images, where red regions contributed the most to the classification. Every heatmap is normalised separately, so the colours cannot be compared between images.

\subsection{Models and Example Selection}
\label{subsec:gradcam_setup}

For each component, the architecture with the highest mean macro-averaged F1 test score in the leave-one-facility-out experiment (Section~\ref{sec:exp_lofo}) was selected for analysis using one of the held-out test sets. For the clarifiers, Fisantekraal was used, since it contains all four clarifier classes, and for the aerobic zones, Waterval was used, since it has the most aerobic zone images. For each class, one correctly classified image was chosen at random, along with one image from each of the most common mistakes. The heatmaps are calculated for the assigned class, so for a mistake they show what the model took as evidence to arrive at its incorrect decision.
